Yes to both questions. Glossaries, ontologies and knowledge graphs will help, but not mainly by making answers more accurate. A Reviewer AI assistant can run the interactive review, though nobody has yet published a tested, complete version of one.

**Will glossaries, ontologies and knowledge graphs help?**
- **Glossary:** clearly helps every journey. It maps synonyms and abbreviations in user questions to the manuals' terms, provides definitions, and is the basis for detecting terminology drift.
- **Ontology:** helps when it is a small core schema owned by people. It lets the assistant scope answers by product, version and role, and ask clarifying questions. Fully automatic ontology building is weak: building the concept hierarchy scores only about 0.12–0.66 on the standard F1 accuracy measure.
- **Knowledge graph:** improves answers only a little, and only for multi-hop, comparison and time-ordering questions. Graph retrieval loses on the simple factual, procedural and definitional questions that make up most manual Q&A. When graph summaries drive the answer, it also gets "this isn't documented" right much less often (about 14% vs 91% with plain search). Where the graph really pays off is as the backbone for finding quality issues and structuring the review.
- **Quality issues:**
  - Rule-based checks find undefined terms, structural gaps and deprecated terms well.
  - An LLM alone finds only about 64% of contradictions, and about 31% of what it flags is noise. A better approach is to extract facts tagged with product and version, then compare them with rules.
  - Users should see conflicts from a pre-computed issue list, because LLMs don't reliably notice them while answering.

**Can a Reviewer AI assistant drive the review?**
- Every part of it already exists somewhere: research prototypes, and products such as TopBraid EDG's problem-and-suggestion panel and PoolParty's accept/reject suggestions.
- The main risks are human, not technical:
  - Reviewers tend to approve wrong suggestions.
  - The assistant tends to agree with the admin's corrections even when they are wrong.
  - Fatigue sets in after roughly 100 items.
- The report's design advice:
  - Store the review queue and its state in a database, not in the conversation.
  - Show the source excerpt behind every proposal.
  - Review the highest-impact, least-certain items first.
  - For key items, have the admin decide before seeing the AI's opinion.
  - Require a second approver for merges and deletions.
  - Turn approved decisions into regression tests for later extraction runs.

**Suggested build order:** glossary, a graph of the manuals' own structure (contents, numbered steps, menu paths, cross-references), combined semantic-plus-keyword search, rule-based issue detectors, and a way to measure answer quality. Add a full GraphRAG-style index later, and only if measurements show you need it.

No public benchmark uses user manuals, and several of the figures are self-reported or weren't checked against the full papers. Testing on your own manuals early will tell you more than the published numbers can.

Both goals are achievable for the content your teams decide on: glossary, taxonomy, ontology, SHACL rules, mappings and hand-curated graph facts. Git can be the system of record for all of it, with governed releases that keep every previous state. The evidence is strong: the FIBO finance ontology and the OBO biomedical ontologies have both worked this way for years with actively maintained tools.

**Three limits shape the design:**
1. **Harvested instance data doesn't belong in git.** Data from Backstage, CRDs and Terraform changes daily. Each harvest run instead goes into its own named graph, with a record of where it came from and a diff against the previous run. A run becomes "current" only after it passes SHACL validation and a check for unusually large deletions, since those usually mean the harvester failed. Changes that need a new class or term become automatic pull requests for review; everything else is just logged. The rule is: content you decide goes in git, content you observe goes in the store.
2. **No maintained tool can merge RDF changes from two teams by meaning.** The recommendation is to prevent conflicts rather than resolve them:
   - every file is rewritten in one fixed order on each commit, using a pinned formatter (EDM Council rdf-toolkit or Cool RDF), so diffs stay readable;
   - each team owns its own modules, enforced through CODEOWNERS;
   - CI requires the other owner's review when two branches change the same terms;
   - a merge queue re-validates the combined result before it lands.
3. **There is no published rule for what counts as a "breaking" change** in a glossary, SHACL rules or mappings. The report proposes a matrix per artifact type, but that is our own design, not a standard. For example, tightening a SHACL rule breaks whoever produces the data, and loosening one breaks whoever relies on the guarantee.

**Recommended setup:**
- **Versioning:** one version number covers everything released together, using major.minor.patch. CI works out the minimum change class from the diff, and the Reviewer AI can raise that class but never lower it. Terms marked "provisional" aren't covered by the compatibility promise.
- **Deprecation:** never delete or reuse a term's identifier. A retired term keeps its definition and points to its successor, and its old name stays searchable on the successor. It leaves the active views no earlier than the next major release plus an announcement window of about 90 days.
- **Releases:** follow the FIBO/OBO pattern:
  - stable identifiers for terms, plus a versioned identifier for each release;
  - release bundles that never change after publication;
  - persistent web addresses that redirect to the right version;
  - a changelog generated from structured change records (KGCL).
- **Governance:** approval thresholds depend on the change class. For major changes, the human records their own classification before seeing the AI's.
- **"As of" answers:** each release is loaded into its own named graph. Every answer, validation report and quality issue records the ontology release, the git commit and the data snapshot it used. Recording only the ontology version isn't enough to reproduce an answer. No published system stamps LLM answers this way, so this part would be new.
- **Tools to avoid:** turtle-formatter, Ecco, Blazegraph, Quit Store, R43ples, OSTRICH and Stardog's built-in versioning, which have been archived, dropped or show no recent releases. The rdf-delta server says it will be archived. TerminusDB and ConVer-G are worth watching but not adopting yet.

The approval thresholds, the 90-day window and the breaking-change matrix are design proposals, not established standards. ## How it meets your expectations

**Start and stop each app separately.**
- Each app has its own `Dockerfile` and its own `Makefile` with `run`, `test` and `lint` targets.
- The root `compose.yaml` gives each app its own profile, so you can run `docker compose --profile assistant up`.

**The apps share data, not components.**

- Each app has its own dependency file and lockfile. There is no root workspace and no shared library folder. That keeps "just one small shared util" from appearing.
- A CI check fails any file in `apps/X` that references `apps/Y`.
