# Put meaning in git, snapshot the harvest

Yes, git can be the system of record for the platform assistant's curated semantic layer: glossary, taxonomy, ontology, SHACL rules, mappings and hand-curated graph facts, all stored in standard formats. Release-based governance with immutable versions is feasible with mature, actively maintained tools. Two communities have run this model for years. FIBO keeps a multi-team OWL program in git with a canonicalising pre-commit serializer, dated version IRIs per module and maturity levels ([FIBO guide](https://github.com/edmcouncil/fibo/blob/master/ONTOLOGY_GUIDE.md)). OBO/ODK automates PR checks, semantic diffs posted as PR comments, and immutable dated releases ([OBO Academy](https://oboacademy.github.io/obook/howto/github-actions); [OBO FP-004](https://obofoundry.org/principles/fp-004-versioning.html)). Three limits shape the design. First, **harvested instance data does not belong in git**. Daily churn from Backstage, CRDs and Terraform goes into named graphs per harvest run, with patch-style diffs and pinned snapshots, and the dedicated versioned triplestores are mostly dormant research code. Second, **semantic merge is unsolved**. No maintained RDF merge driver exists, so conflicts must be prevented by deterministic serialization, team-owned modules and post-merge revalidation, not resolved by tooling. Third, **no standard defines "breaking"** for SKOS, SHACL or mappings. The policy below adapts Health-RI's test (do previously valid instances, queries or inferences change?) to each artifact type, and it is a design proposal rather than established practice ([Health-RI](https://health-ri.github.io/semantic-interoperability/method/ontology-versioning)). The practical result is a release train with SemVer tags, stable term IRIs, never-delete deprecation, CI that computes a floor for the change class, and a Reviewer AI that can raise that class but never lower it. Every assistant answer is stamped with the ontology release and data snapshot it used, so "why did the answer change?" becomes a lookup.

This report extends the architecture in *Enterprise platform domain assistants*: LinkML as schema source, voc4cat for spreadsheet-edited SKOS, harvest-propose-review bot PRs, the semantic council and per-team stewards, and a Reviewer that never commits. It also extends the versioning principles in *Domain assistants for emerging cross domains* (obsolete-and-replace, answers stamped with a release) and the review safeguards in *Knowledge graphs for domain assistants*. It specifies the change-management mechanics those reports left open.

## Feasible for curated meaning, weak for semantic merge and versioned stores

Evidence strength here rates whether a *published, running practice or maintained tool* supports each part of the design. It does not rate whether the idea is attractive.

| Question | Verdict | Evidence strength | Main risk |
|---|---|---|---|
| Store glossary, taxonomy, ontology, SHACL and mappings in git in standard formats | **Yes** | Strong: FIBO, OBO/ODK, schema.org, QUDT and Finto-data all run active git repositories in Nov 2026 ([schemaorg](https://github.com/schemaorg/schemaorg); [QUDT](https://github.com/qudt/qudt-public-repo); [Finto-data](https://github.com/NatLibFi/Finto-data)) | Editor re-serialization noise; non-ontologists editing Turtle |
| Readable line diffs on RDF | **Yes, only with a canonical serializer** in pre-commit and CI | Strong: rdf-toolkit is FIBO's reference serializer ([rdf-toolkit](https://github.com/edmcouncil/rdf-toolkit)) | Blank nodes; tool version drift changing output |
| Semantic diff for review | **Yes** (ROBOT diff, OAK/KGCL) | Strong for OWL ([ROBOT diff](https://robot.obolibrary.org/diff)); moderate for SKOS/SHACL (generic triple diffs) | Diffs show triples, not intent, unless composite changes are recorded |
| Semantic merge across concurrent team PRs | **No tool; prevent instead** | Weak: research prototypes only ([Quit Store](https://arxiv.org/abs/1805.03721v3)) | Clean text merges that are semantically contradictory |
| Change classification and SemVer per artifact | **Yes as policy**, partly automatable | Moderate: OBO, Health-RI, schema.org and DCAT-AP publish policies; none covers SHACL | Class inflation (everything MAJOR) or under-classification |
| Never-delete deprecation | **Yes** | Strong: OBO, SNOMED, schema.org converge ([OBO FP-019](https://obofoundry.org/principles/fp-019-term-stability.html); [SNOMED](https://docs.snomed.org/snomed-ct-practical-guides/snomed-ct-terminology-services-guide/4-terminology-service-types/4.11-get-history-data)) | Deprecated terms lingering in docs, prompts and shapes |
| Release mechanics (version IRIs, tags, artifacts, PURLs) | **Yes** | Strong: ODK release artefacts, w3id ([OBO Academy](https://oboacademy.github.io/obook/reference/release-artefacts/); [w3id](https://github.com/perma-id/w3id.org)) | Broken version-IRI resolution over time |
| Harvested instance data versioned in git | **No; use run graphs plus snapshots** | Moderate by inference: git-backed RDF stores exist but are dormant ([QuitStore](https://github.com/AKSW/QuitStore)) | Treating every harvest delta as a PR swamps reviewers |
| "As of" querying and reproducible answers | **Yes with named graph per release**; no dedicated store needed | Moderate: SPARQL named graphs are universal; no published LLM assistant stamps answers this way | Storage growth; forgetting to pin data snapshot as well as schema |
| AI reviewer in ontology PR governance | **Feasible as advisory classifier and drafter** | Weak: KGCL agent and ODK-AI as precedents; LLM change benchmarks are early ([KGCL](https://arxiv.org/abs/2409.13906); [CEUR Vol-4316](https://ceur-ws.org/Vol-4316/pd-short-8.pdf)) | Automation bias; under-classifying breaking changes |

The pattern repeats the earlier reports' finding. Mechanics that govern *identity and form* (IRIs, serialization, deprecation, release artifacts) are mature and borrowable. Anything that requires judging *meaning*, such as whether a merge contradicts or whether a definition change shifts referents, stays a human decision supported by deterministic checks.

## Git holds what people decide; the store holds what harvesters observe

### The dividing line is curation, not RDF layer

The split is not "TBox in git, ABox in the store". It is "decided content in git, observed content in the store". Git holds everything a person approves: LinkML schema modules, SKOS schemes, hand-written SHACL profiles, the kind-mapping table, harvester mapping configurations and JSON-LD contexts, and *curated* instance facts. Curated facts include capability-realisation statements, ownership corrections, overlap rulings and accepted overrides. The triple store holds what harvesters observe every day: services, instances, versions, replica counts and ownership edges copied from the portal. Quit Store shows that a git-backed SPARQL store is possible, but its last release dates from 2022 and its repository was last pushed in June 2024 ([QuitStore](https://github.com/AKSW/QuitStore)). Its design targets collaborative editing, not bulk ETL. The established alternative is to write each harvest run into its own named graph with PROV-O run metadata, keep diffs between runs as add/delete sets, and pin immutable dated snapshots for releases. This is the DBpedia Databus pattern of artifact plus version ID, where ISO-like IDs sort chronologically ([Databus](https://dbpedia.gitbook.io/databus/model/versioning)).

Harvest deltas are not pull requests, but they are still governed, at run granularity. A run graph such as `urn:harvest:backstage:2026-11-13T02:00Z` is promoted to the source's `current` graph only after a gate passes: SHACL against the released shapes, plus a volume check that quarantines runs in which a large share of entities disappear. A mass disappearance usually means a harvester or credential failure, not a real decommissioning. Changes that cross the schema boundary become bot PRs into git, as the earlier report's harvest-propose-review loop prescribes. Examples are a new CRD kind, a new Terraform resource type, a Backstage `spec.type` with no mapping, or a CRD version deprecation. Each PR carries a proposed class or concept stub, sample instances and the run ID as evidence. The thresholds are illustrative; no published benchmark for "meaningful change" in platform catalogs exists. Instance diffs can borrow DataHub's semantic categories, where each change transaction is tagged MAJOR, MINOR or PATCH ([DataHub Timeline](https://docs.datahub.com/docs/dev-guides/timeline)). For instances, removal or change of kind or owner counts as MAJOR, a new entity or relation as MINOR, and a label or description change as PATCH. These categories drive notifications, not approvals.

### One monorepo for the core and platform modules, separate repos for product teams

The repository mirrors ownership, because CODEOWNERS is the cheapest federated-governance enforcement available. FIBO's one-file-per-module layout fits team ownership. One file per concept multiplies import and catalog overhead and has no established precedent for OWL; none was found for SKOS either.

```text
semantic-core/                       # one release train, one version for all co-released artifacts
  schema/core/*.yaml                 # LinkML core: council CODEOWNERS
  schema/platform/<team>/*.yaml      # team modules: team steward CODEOWNERS
  vocab/<scheme>.ttl                 # SKOS, canonical Turtle (spreadsheet is an editing view)
  shapes/profiles/*.ttl              # hand-written SHACL: SKOS profile, collisions, overlap rules
  mappings/kinds.tsv                 # curated kind mapping (harvested type -> canonical concept)
  kg/curated/*.ttl                   # decided instance facts: realises, ownership overrides, rulings
  harvest/config/, harvest/context/  # harvester mappings, JSON-LD @context files
  tests/competency/*.rq              # SPARQL ASK/SELECT with expected results
  changes/<pr-number>.kgcl.yaml      # machine-readable change record per PR
  migrations/vX.Y.Z/*.ru             # idempotent SPARQL Updates for renames/merges
  CHANGELOG.md  CODEOWNERS  .pre-commit-config.yaml
```

Generated artifacts (OWL, SHACL and the JSON-LD context from LinkML, and the reasoned "full" ontology) are built in CI and attached to releases, not committed on `main`. Committing them doubles every diff and invites hand edits to generated files. The exceptions are hand-authored Turtle files, which are the reviewed source and must be canonical. The voc4cat spreadsheet route from the earlier report remains the editing path for terminology stewards, but the canonical Turtle is what git reviews. A binary `.xlsx` in git produces no readable diff. Whether voc4cat's own workflow already treats Turtle as the committed source was not verified. Product teams keep separate repositories from the template, import the core by version IRI, and pin a core release, much as OBO ontologies import extracted modules from each other.

### Deterministic serialization is non-negotiable

RDF has no inherent triple order, so the same graph can be written in many valid ways. Without canonicalization, git shows false changes and false conflicts. The turtle-formatter README names exactly this problem ([turtle-formatter](https://github.com/atextor/turtle-formatter)), and the SerVCS work showed that git raises false-positive conflicts on differently serialized copies of the same ontology ([SerVCS](https://www.scitepress.org/Papers/2016/60546/)). Two maintained serializers fit. **EDM Council rdf-toolkit** is FIBO's reference serializer. It writes ontology-header triples first, sorts by subject, predicate and object, names blank nodes `blankXXX`, outputs Turtle, RDF/XML or JSON-LD, and ships a git pre-commit hook. It was last pushed in January 2026, with release v2.0 from April 2024 ([rdf-toolkit](https://github.com/edmcouncil/rdf-toolkit)). **Cool RDF** (formerly owl-cli and turtle-formatter, v2.0.1 July 2026) gives configurable subject, predicate and prefix order, for example `rdf:type` and `skos:prefLabel` first, which makes Turtle easier for humans to review ([cool-rdf](https://github.com/cool-rdf/cool-rdf)). Pick one, pin its version, run it in pre-commit, and add a CI check that fails when re-serializing changes any file. A serializer upgrade then becomes its own reformat-only PR rather than noise spread across feature PRs. FIBO's guide shows the failure mode: Protégé strips entity declarations and abbreviations, and these "must be rectified prior to checking in" ([FIBO guide](https://github.com/edmcouncil/fibo/blob/master/ONTOLOGY_GUIDE.md)).

Blank nodes are the main source of diff noise. Curated content should use IRIs wherever it can: concepts, SHACL property shapes (which can be IRIs) and notes. Unavoidable blank nodes such as OWL restrictions and RDF lists should be inlined under a named subject. W3C RDF Dataset Canonicalization (RDFC-1.0, a Recommendation since May 2024) relabels blank nodes deterministically and outputs canonical N-Quads ([W3C RDFC-1.0](https://www.w3.org/TR/rdf-canon/)). Use it for content hashes ("did this graph actually change?", snapshot fingerprints, signing), not as the reviewed format. Its implementations can differ on language-tag case, and the hash algorithm must be stated for reproducibility.

## Text diffs are solved, semantic merges must be prevented

Once serialization is canonical, line diffs work for review, and a semantic diff should be added as the human-readable PR summary. `robot diff` ignores file-structure differences and emits markdown, html or label-annotated output. It can compare against a published release IRI, so a PR can be diffed against the last release rather than only against `main` ([ROBOT diff](https://robot.obolibrary.org/diff)). OBO projects post this markdown as a PR comment from a GitHub Actions workflow ([OBO Academy](https://oboacademy.github.io/obook/howto/github-actions); [Balhoff gist](https://gist.github.com/balhoff/6c0d434b1601de4d4006bff76b858ac1)). KGCL adds a machine-readable, LinkML-based change language with both a data model and a controlled natural language. Examples are `add synonym 'arm' to 'forelimb'` and `move 'Parkinson disease' under 'neurodegenerative disease'`. It is used both to request changes and to describe diffs ([KGCL paper](https://arxiv.org/abs/2409.13906); [kgcl repo](https://github.com/INCATools/kgcl)). Its companion library OAK is active at v0.7.4 ([OAK](https://github.com/INCATools/ontology-access-kit)). KGCL is the recommended change-record format here because it is LinkML-native, records *composite* operations such as rename, move, merge and obsolete-and-replace, and doubles as the input format for AI-proposed edits. Whether `oak diff` emits KGCL directly in the current release was not verified. A thin custom step that turns ROBOT or triple diffs into KGCL may be needed.

Merge is where the tooling stops. Quit Store's research showed that a three-way merge on atomic graphs can succeed textually yet introduce semantic contradictions. Its "Context Merge" strategy instead flags a conflict whenever both branches touched the same node ([arXiv 1805.03721](https://arxiv.org/abs/1805.03721v3)). No maintained RDF or Turtle git merge driver was found. `oxirs merge` does set-union merges with same-subject-predicate conflict reports, but it is a standalone tool ([oxirs](https://docs.rs/crate/oxirs/latest/source/src/commands/merge_command.rs)). Cross-team concurrency is therefore handled by four layers of prevention. **Canonical serialization** removes false conflicts. **Module ownership** with CODEOWNERS removes most true ones, because two teams rarely edit the same file. **A Context-Merge rule in CI** catches the rest: diff base→PR and base→`main` HEAD, intersect the changed subject IRIs, and require the other owner's review if the intersection is non-empty. **A merge queue** re-runs reasoning, SHACL and competency tests on the actual post-merge state, because two individually green PRs can be jointly inconsistent, for instance one adds a disjointness and the other a subclass. The intersection rule is cheap and deterministic, and it is a natural item for the Reviewer AI to explain. A custom `.gitattributes` union driver is only safe for sorted N-Triples files where both sides only add lines, which rarely applies to curated content.

Real semantic disputes are a different matter: two platforms defining "environment" differently, or claiming the same capability. These are not merge conflicts. They follow the earlier reports' rule that each meaning becomes a scoped definition record attributed to its platform, and contested status goes to the semantic council.

## Classify every change by what it breaks, and let CI set the floor

### The change model has two axes and four record layers

Every change has an *operation*, either atomic (add or remove one axiom, label or triple) or composite (rename, move, merge, split, obsolete-and-replace). It also has an *effect*: editorial, additive or breaking. Noy and Klein argued two decades ago that ontology evolution differs from schema evolution largely because of composite operations ([Noy & Klein](https://research.vu.nl/en/publications/ontology-evolution-not-the-same-as-schema-evolution/)). If a rename is recorded only as "delete label, add label", the assistant can no longer tell a user that something *was renamed*. The change is recorded in four complementary layers. The KGCL record per PR states the operation. Entity-level annotations live in the artifact itself: `owl:deprecated`, `dcterms:isReplacedBy`, `skos:changeNote` for fine-grained maintenance and `skos:historyNote` for meaning-level change that users should see ([SKOS Primer](https://www.w3.org/TR/skos-primer/)). An ontology or scheme header per release carries `owl:versionIRI`, `owl:versionInfo`, `owl:priorVersion` and `owl:incompatibleWith`; these OWL compatibility properties are annotations with no enforced semantics ([OWL 2](https://www.w3.org/TR/owl2-syntax/)). Finally, a PROV-O release activity links the PR, the approvers, the Reviewer AI agent and the commit SHA ([PROV-O](https://www.w3.org/TR/prov-o/)).

### SemVer per release train, with an explicit breaking matrix

OBO prefers ISO-date version IRIs and allows SemVer ([OBO FP-004](https://obofoundry.org/principles/fp-004-versioning.html)). This system's consumers include the assistant, the Vale vocabulary package, product-team imports, harvesters and SHACL-validated data producers, and they need a compatibility signal. The recommendation is therefore **SemVer tags (`vX.Y.Z`) on a single release train**, with the release date in `dcterms:issued`. As Health-RI does, one version identifier covers all co-released artifacts: OWL, SHACL, SKOS, JSON-LD context and docs ([Health-RI](https://health-ri.github.io/semantic-interoperability/method/ontology-versioning)). Per-module versions multiply compatibility combinations that no team will test. Health-RI's classification test is the core rule. A change is semantic if it alters logical consequences or constraints, makes previously valid instances invalid or the reverse, or changes identity or meaning. That test cannot be applied mechanically to every artifact, so the matrix below specialises it. It is this report's proposal; no published SemVer policy exists for SHACL or mappings.

| Artifact | PATCH (no semantic effect) | MINOR (additive, compatible) | MAJOR (breaking) |
|---|---|---|---|
| SKOS glossary/taxonomy | Typo, formatting, example, changeNote, scopeNote | New concept; new altLabel or hiddenLabel; new leaf under an existing broader; definition clarified with the same referents; deprecation with replacement | Changing a prefLabel that consumers key on; merge or split; moving a concept to a different broader (changes `broader*` closure queries); removing a label that lint or synonym expansion relies on |
| OWL ontology | Annotation fixes | New class or property; new subclass under existing class; deprecation with replacement | Removing or renaming an IRI; changing domain or range; adding disjointness; changing a superclass; changing property characteristics (functional, transitive); anything that changes entailments on existing data |
| SHACL shapes | Message text; documentation | New optional property shape; loosening (minCount 1→0, wider `sh:in`); new shape targeting only a new class | Tightening (minCount 0→1, lower maxCount, narrower datatype, pattern or `sh:in`, `sh:closed true`); raising severity from Warning to Violation; a new shape on an existing class. Mechanically: **any new violation on the current KG snapshot** |
| Mappings (kind table, `skos:exactMatch`/`closeMatch`) | Comment or justification text | New mapping for a previously unmapped harvested type; new closeMatch | Re-pointing a harvested type to another concept (reclassifies instances); weakening exactMatch to closeMatch or removing it (shrinks synonym expansion); deleting a mapping |
| JSON-LD context | Formatting | New term | Removing a term or changing a term's `@id` or `@type` coercion (silently changes the RDF of existing JSON) |
| Curated KG facts | Provenance fixes | New realisation, ownership or ruling facts | Re-identifying or removing a node; changing a fact that past assistant answers cited |

SHACL runs in the opposite direction from OWL. Tightening a shape breaks *data producers* (harvesters and team catalogs), while loosening one breaks *consumers* who relied on the guarantee. The second case is rare enough to handle by review. Maturity staging keeps the matrix from turning every new service into a MAJOR release. FIBO marks modules as Release or Provisional and builds Production from Release modules only ([FIBO process](https://spec.edmcouncil.org/fibo/page/development-process)), while schema.org stages new terms in "Pending" and retires old ones to the "Attic" ([schema.org releases](https://schema.org/docs/releases.html)). Terms flagged `provisional` here are excluded from the compatibility promise, and the assistant labels them as such in answers.

CI computes a **floor** for the class from deterministic signals. Removed IRIs without deprecation fail outright. A non-empty IRI-set difference, new SHACL violations on the snapshot, changed superclasses or disjointness, and re-pointed mappings each force MAJOR. New IRIs force at least MINOR. The proposer declares a class in the PR template, and the Reviewer AI proposes one after reading the diff and definitions. The effective class is the maximum of the three, and **the AI may raise but never lower the computed floor**. Disagreement between proposer and AI is surfaced to the approver rather than silently resolved. One judgment cannot be automated: whether a reworded definition changes its referents. OBO's rule is that if the referents change, the term gets a new IRI and the old one is obsoleted, and that is the Reviewer's most valuable flag ([OBO FP-019](https://obofoundry.org/principles/fp-019-term-stability.html)).

### Deprecation: never delete, always point somewhere

Every mature community converges on the same policy. OBO sets `owl:deprecated true`, keeps the definition, strips logical axioms, and points to a replacement through "term replaced by" (exact) or `consider` (inexact). It also pre-announces obsoletions, and its dashboard flags terms that still reference obsolete ones ([OBO FP-019](https://obofoundry.org/principles/fp-019-term-stability.html)). Mondo uses `consider` when the successor is not equivalent ([Mondo](https://mondo.readthedocs.io/en/latest/editors-guide/merging-and-obsoleting/)). SNOMED never deletes and records a reason plus a typed historical association: SAME AS, REPLACED BY, POSSIBLY EQUIVALENT TO ([SNOMED](https://docs.snomed.org/snomed-ct-practical-guides/snomed-ct-terminology-services-guide/4-terminology-service-types/4.11-get-history-data)). schema.org deprecates first, moves terms to the Attic and records supersession in release notes ([schema.org](https://schema.org/docs/releases.html)). For the platform glossary and ontology, the policy is as follows. IRIs are never deleted or reused. A deprecated term gets `owl:deprecated true`, `dcterms:isReplacedBy` for an exact successor or `rdfs:seeAlso` for candidates, and a `skos:historyNote` with the reason, release and date. It keeps its `skos:definition`. Its old prefLabel moves to `skos:hiddenLabel` on the successor, so search, synonym normalisation and the generated Vale substitution rule ("use X instead of Y") still recognise the old name. Removal from *active* views, SHACL targets and lint allow-lists comes no earlier than the next MAJOR release and at least one announced window, for example 90 days. That window is a choice, since OBO pre-announces without fixing a duration. A retired platform service is a different case: the real thing ended. It is not "deprecated in favour of" anything unless a successor exists. It stays as a historic entity with an end date, which keeps "what did we use in 2025?" answerable.

### Impact analysis is a dependency closure plus a re-validation

The ontology-evolution literature treats impact assessment and change propagation as distinct stages after validation ([Zablith et al.](https://www.cambridge.org/core/journals/knowledge-engineering-review/article/abs/ontology-evolution-a-processcentric-survey/CE4387A954917B7CA3282CE25FAC09FA)). In a git setup, both reduce to a computed procedure. Take the changed-IRI set from the diff. Search for every dependent that references those IRIs, in git and in the deployed KG. Re-run validation. Then generate migrations. Most dependents in this system are not RDF, and **no published tool computes impact on prompts, docs or answer caches**, so this part is custom work.

| Dependent | Detection | Propagation |
|---|---|---|
| SHACL shapes | IRI in `sh:targetClass`, `sh:path`, `sh:class`, `sh:in` | Update shapes; re-validate full KG snapshot; list new violations |
| KG instances (harvested and curated) | SPARQL count of triples using the IRI | Idempotent SPARQL Update in `migrations/vX.Y.Z/`, tested in CI against a snapshot |
| Mappings and harvester configs | Reverse lookup in `mappings/` and `harvest/config/` | Flag the mapping owner; harvester must ship before or with the release |
| Vale vocabularies | Label diff | Regenerate accept, reject and substitution lists on release |
| Doc pages | `core:mentions` links from the earlier report, plus text search | "Review needed" task on the owning page |
| Assistant prompts, SPARQL templates, tool descriptions | Text and IRI search | Owner notification; prompt and competency regression tests |
| Answer cache and vector index | Answers tagged with release and IRIs used | Invalidate only entries citing changed IRIs; re-embed changed definitions |
| Product-team repositories | Import manifests and pinned versions | Notify subscribers; they upgrade on their own schedule |

The Reviewer AI posts this table, filled in, as a PR comment. A MAJOR change cannot merge without a populated migration directory or an explicit "no migration needed" justification.

## A release is an immutable bundle, built and checked by a ten-stage pipeline

### Release mechanics follow ODK and FIBO

Term IRIs never carry versions; only the ontology and release artifacts do. FIBO keeps resource IRIs stable and embeds a date in each module's versionIRI ([FIBO guide](https://github.com/edmcouncil/fibo/blob/master/ONTOLOGY_GUIDE.md)). ODK stamps every artifact with an ontology IRI and a `releases/<date>/` versionIRI ([OBO Academy](https://oboacademy.github.io/obook/reference/release-artefacts/)). The equivalent here is a stable ontology IRI per module (`https://w3id.org/acme/platform/core`) and a versionIRI per release (`.../core/releases/3.2.0/core.ttl`). `owl:versionInfo` carries the tag, `owl:priorVersion` the previous versionIRI, and `owl:incompatibleWith` is added on MAJOR. Each release is a git tag plus a release page whose attached artifacts are immutable, following OBO's rule that released files are never altered and fixes go into a new release ([OBO FP-004](https://obofoundry.org/principles/fp-004-versioning.html)). The bundle contains the reasoned "full" ontology, the "base" module-only file, the SKOS export, SHACL shapes, the JSON-LD context at a versioned URL, the KGCL change set, the PROV-O release record and generated documentation. Documentation comes from Widoco (v1.4.26) or pyLODE (3.6.1) for OWL and Skosmos (v3.5) for SKOS, all maintained ([Widoco](https://github.com/dgarijo/Widoco); [pyLODE](https://github.com/RDFLib/pyLODE); [Skosmos](https://github.com/NatLibFi/Skosmos)). Redirects run from each versionIRI to the tagged artifact and from the unversioned IRI to the latest release. They can live on w3id.org, which is managed by PRs to a very active GitHub repository ([w3id](https://github.com/perma-id/w3id.org)), or on an internal PURL server for private namespaces. CI checks that every past versionIRI still resolves, as OBO does. The changelog is generated from the PR's KGCL records and grouped Breaking / Deprecated / Added / Changed / Fixed, with links to PRs. That matches EU Vocabularies' requirement that each publication package carry release notes ([EU Vocabularies](https://op.europa.eu/en/web/eu-vocabularies/advanced-learners)).

The cadence borrows DCAT-AP's cut-off rule, where requests that arrive after the cut-off roll to the next release ([DCAT-AP policy](https://interoperable-europe.ec.europa.eu/collection/semic-support-centre/solution/dcat-application-profile-data-portals-europe/document/change-and-release-management-policy-dcat-ap)). A monthly MINOR train has a cut-off. MAJOR releases come at most quarterly, FIBO-like, with a deprecation calendar. PATCH releases ship on demand. schema.org's 29.1 and 29.2 show why: patch releases exist to fix regressions in the previous release ([schema.org](https://schema.org/docs/releases.html)). On release, the store loads the bundle into its versioned named graph, the Vale package is regenerated, and subscribers whose dependents appeared in an impact report are notified.

### The CI pipeline separates blocking gates from advisory output

| # | Stage | Tool | Blocking? |
|---|---|---|---|
| 1 | Parse all RDF; canonical-serialization check (re-serialize, fail on diff) | rdf-toolkit or Cool RDF, pinned | Yes |
| 2 | LinkML lint and generation (OWL, SHACL, JSON-LD context) | LinkML 1.12.1 ([LinkML](https://github.com/linkml/linkml)) | Yes |
| 3 | Reasoner consistency and unsatisfiable classes | `robot reason` (ROBOT 1.9.11) ([ROBOT](https://github.com/ontodev/robot)) | Yes |
| 4 | QC report with custom profile (labels, definitions, deprecated-reference use) | `robot report`; FIBO-style hygiene SPARQL ([FIBO guide](https://github.com/edmcouncil/fibo/blob/master/ONTOLOGY_GUIDE.md)) | ERROR level |
| 5 | SHACL: SKOS profile and collision shapes over vocab; new shapes over current KG snapshot | pySHACL 0.40.2 ([pySHACL](https://github.com/RDFLib/pySHACL)) | Yes; new KG violations force MAJOR |
| 6 | Deprecation lint (replacement present, no dangling references, label moved to hiddenLabel) | SPARQL `verify` queries | Yes |
| 7 | Competency-question regression | `robot verify` or pytest over SPARQL | Yes |
| 8 | Breaking-change floor: IRI-set diff vs last tag, superclass and disjointness changes, mapping re-points | Custom script over ROBOT/OAK diff | Sets class; fails on undeclared removals |
| 9 | Context-Merge check: changed subjects intersecting `main`'s recent changes | Custom | Requires extra reviewer |
| 10 | Semantic diff and impact report as PR comment; Reviewer AI review | `robot diff -f markdown`, KGCL, Reviewer | Advisory |

Stages 1–7 are the ODK and FIBO pattern ([OBO Academy](https://oboacademy.github.io/obook/howto/github-actions)). Stages 8–10 are this system's additions. A merge queue re-runs 1–9 on the merged result. No benchmark was found for reasoning time on modules of this size, so the pilot should measure it. If ELK-class reasoning becomes slow, a split between per-PR and nightly runs may be needed.

## Humans approve by impact class, and the Reviewer AI argues the case

The roles are the earlier report's: semantic council, platform-team terminology stewards, the DevEx/docs enabling team, journey owners, optional product-team stewards, and a Reviewer AI that owns nothing and never commits. What this report adds is the workflow those roles run. A **proposal** is a PR from a person, from a harvest bot (TBox-impacting drift), or from the Reviewer queue (an accepted collision fix). Its template carries the KGCL operation, affected IRIs, rationale and evidence, the declared class, the replacement for any deprecation, a migration flag and the owning team. **CI** then runs the ten stages. The **Reviewer AI** posts its classification, the filled impact table, drafted `historyNote`/`changeNote` text and changelog entry, a deprecation-hygiene check and, for definition edits, an explicit "same referents?" judgment with its reasoning. **Approval** follows the effective class.

| Effective class | Required approval | Extra conditions |
|---|---|---|
| PATCH | 1 steward of the owning module | Any CI-green state |
| MINOR, own module only | Owning steward | Context-Merge hit adds the other module's steward |
| MINOR touching core, shared mappings or another team's IRIs | Owning steward + 1 cross-team reviewer or council member | — |
| MAJOR (any artifact) or SHACL change producing new violations | Council quorum (e.g. 2 stewards + chair) | Migration in `migrations/`, deprecation notice, announcement window, scheduled on the MAJOR train |
| Emergency (harmful wrong definition in live answers) | 1 steward, post-hoc council review | Ships as PATCH, or as an assistant-side suppression; never a destructive edit |
| Harvest drift (instance-level) | None per change | Run-level gate; quarantined runs go to the Reviewer queue |

These thresholds are a design proposal. OBO, FIBO and schema.org publish their processes but not approval counts. Health-RI's stage gates add one useful rule: any semantic change reverts a package to an internal review stage ([Health-RI](https://health-ri.github.io/semantic-interoperability/method/ontology-versioning)). The equivalent here is that a MAJOR change to a `release`-maturity module re-enters review even if its author is the owning steward. The council's decision SLA from the earlier report applies to MAJOR items, so the train does not stall.

The Reviewer AI's value is in what it reads, not what it decides. The impact table, the Context-Merge intersection and the "did this definition change its referents?" flag are where human reviewers are most likely to miss something. Two safeguards from the earlier reports become concrete here. Measured automation bias means a wrong AI suggestion lowers reviewer accuracy ([arXiv 2507.14552](https://arxiv.org/pdf/2507.14552v1)). So for MAJOR items the council member records a class before the AI's classification is revealed (decide-before-reveal), and the review log tracks how often humans and the AI disagree. The rule that the AI can only raise the CI-computed floor stops a sycophantic or wrong model from waving a breaking change through as MINOR. KGCL's GitHub agent and ODK-AI show that machine-applied changes under human approval already work in ontology repositories ([KGCL](https://arxiv.org/abs/2409.13906); [ODK-AI](http://ai4curation.io/odk-ai)). The 2025 LLM change-proposal work (Evo-DKD, TRACE-OU-Bench) is early and does not cover impact analysis ([CEUR Vol-4316](https://ceur-ws.org/Vol-4316/pd-short-8.pdf)). The Reviewer's classification accuracy therefore has to be measured on this repository's own PR history before anyone trusts it. One older tool should not be relied on: `ontobot-change-agent`, the KGCL issue-to-PR bot, was last pushed in December 2024 ([ontobot](https://github.com/INCATools/ontobot-change-agent)).

Git history, PR reviews, KGCL records and the PROV-O release activity together form the audit trail: who changed what, when, why, and who approved. Retention periods depend on the organisation's change-management evidence rules; no platform-specific standard was found.

## Every answer names the release and snapshot it stands on

"As of" querying needs no versioned database. Load each release bundle into a named graph keyed by its versionIRI, for example `GRAPH <https://w3id.org/acme/platform/releases/3.2.0/>`, and keep a `current` alias graph. Asking "as of v3.1" then means `FROM` that graph, and "what changed between v3.1 and v3.2" means a `MINUS` between graphs, or better, a lookup in the KGCL and changelog graph, which keeps the composite intent ("renamed") that triple diffs lose. This works on any SPARQL store. Oxigraph (v0.5.13, Oct 2026) is active ([Oxigraph](https://github.com/oxigraph/oxigraph)), and Fuseki and GraphDB are the scale-up path from the earlier report. Stardog removed its built-in versioning after 7.0 ([Stardog community](https://community.stardog.com/t/versioning-in-stardog-7/1700)). GraphDB's history plugin exists, but its current syntax and edition availability were not verified, and it cannot stage changes for approval ([StackOverflow archive](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/61097427/how-to-set-up-version-control-on-top-of-a-triple-store)).

Instance data needs a time model of its own. The defensible starting point is **observed-at intervals**: the harvest run where an entity was first seen and the run where it was last seen, taken from run-graph timestamps (transaction time). Valid time is added only where a source supplies it, such as a CRD `creationTimestamp`. Graphiti's four timestamps per edge (`valid_at`, `invalid_at`, `created_at`, `expired_at`) are a good template. Contradicted facts are invalidated rather than deleted, and "as of t" becomes a range filter ([Graphiti model](https://mintlify.com/getzep/graphiti/concepts/temporal-model); [Zep paper](https://arxiv.org/html/2501.13956v1)). Statement-level annotation with RDF 1.2 triple terms is the elegant long-term option. RDF 1.2 Concepts was still a Candidate Recommendation in April 2026 ([RDF 1.2](https://www.w3.org/TR/rdf12-concepts/)), and Starvers found that RDF-star query performance "differs vastly" across stores ([SWJ Starvers](https://semantic-web-journal.net/system/files/swj3506.pdf)). It should wait. Storage can follow the IC/CB split from the RDF-archive literature ([Fernández et al.](https://www.semantic-web-journal.net/node/1814)). Keep every daily run diff (small) indefinitely. Keep full snapshots only for release-pinned and answer-cited states. Compact old daily snapshots to weekly. ConVer-G's one-row-plus-version-bitmask idea suits low-churn daily harvests and can be reproduced in plain Postgres ([ConVer-G](https://arxiv.org/pdf/2409.04499)).

Reproducibility then comes from one **context tuple**: `{ontology release + git SHA, shapes release, mapping SHA, data snapshot ID, retrieval time}`. This is lakeFS's "record the commit ID with every run" discipline applied to answers ([lakeFS](https://lakefs.io/blog/scalable-ml-data-version-control-and-reproducibility/)). It is stamped on every assistant answer (footer plus log), on every SHACL validation report (`prov:used` pointing at the shapes and data graph versions), and on every quality issue. Re-checking an old answer or issue means loading that snapshot's graphs with that tag's shapes. FHIR shows why both halves must be pinned: a ValueSet expansion can change under the same business version when an underlying code system changes, unless versions are locked ([FHIR ValueSet](https://www.hl7.org/fhir/ValueSet.html)). An answer pinned only to the ontology release, and not to the data snapshot, is not reproducible. The user-facing payoff follows the second report's design. When a question uses a deprecated or hidden label, the assistant answers with the successor and quotes the `historyNote`: "'Foo Gateway' was renamed 'Edge API Gateway' in v3.0 (2026-06)". SNOMED's history supplements, which let queries include what a concept used to be, are the precedent ([SNOMED ECL](https://docs.snomed.org/snomed-ct-specifications/snomed-ct-expression-constraint-language/examples/6.11-history-supplements)). No published LLM assistant answering "as of version" over versioned vocabularies was found, so this part is new ground.

## Risks concentrate where text tools meet meaning

The largest risk is **silent semantic breakage through green text merges**. Two individually valid PRs combine into an inconsistent ontology, or a "clarified" definition shifts what a term denotes without changing any IRI. The merge queue catches the first. Only the referent-change flag and human judgment catch the second. **Serialization drift** comes next: an editor such as Protégé, a LinkML generator upgrade or a serializer upgrade rewrites files and buries real changes in noise. Pinning tool versions and isolating reformat PRs contain it. Whether Cool RDF's or OWLAPI's output is byte-stable across versions was not verified. **Class inflation and deflation** are mirror risks. A strict matrix makes every small taxonomy move MAJOR, and teams respond by routing work around the train. A lax one breaks product-team imports. Provisional maturity and the CI floor bound both. **Reviewer automation bias** carries over unchanged from the earlier reports and is mitigated as described above. **Harvest-induced damage** to the KG is the operational risk: a broken harvester promoting a mass-deletion run to `current`. The volume gate and quarantine address it. **Dependency on dormant or archiving tools** (rdf-delta, versioned stores) is avoided by design. **IRI resolution rot** over years of releases needs its own CI check. **Storage growth** from per-release graphs and daily runs is bounded by the retention tiers. Finally, there is **governance theatre**. If the council approves MAJOR changes without reading the impact report, the process produces paperwork, not safety. Rubber-stamp indicators from the earlier report's metrics apply here too.

Several questions remain open. Can the definition-referent judgment be made reliable enough to gate on, or is it permanently advisory? Should product-team repositories share the core's release train or version independently, and how many core versions back must the platform support? How should SHACL loosening that removes a consumer guarantee be detected mechanically? Does `oak diff` emit usable KGCL for SKOS and SHACL changes, or must a custom translator be maintained? What retention period do the organisation's audit rules require for answer-cited snapshots? Is the GraphDB history plugin current and usable? Has RDF 1.2 reached Recommendation with adequate store support, which would make statement-level validity practical? And will the monthly MINOR cadence keep up with platform teams' rate of change, or will provisional terms accumulate faster than they graduate?

## Conclusion

The central insight is that "keep everything in git" and "version everything" are different requirements, and they part ways at the curation boundary. Git is excellent at what humans decide and poor at what machines observe. Pushing harvested facts through PRs would bury the decisions that matter under thousands of routine deltas, while keeping curated meaning outside git would lose the review, ownership and audit that git provides almost for free. Splitting the two, then joining them again through a context tuple on every answer, delivers both the governance the platform needs and the reproducibility the assistant needs, without depending on any of the dormant versioned stores.

The second insight is that the hard part of change management is not the version number but the classification behind it. Release mechanics are fully borrowable from FIBO and ODK. What no community has standardised, and what this system must own, is a deterministic floor for "is this breaking?" across SKOS, SHACL and mappings, plus a disciplined way to catch the one breaking change no tool can see: a definition that quietly starts meaning something else. That is where the Reviewer AI earns its place. It is useful not as an approver but as the participant that reads every impact table and asks, on every reworded definition, whether the referents are still the same.
