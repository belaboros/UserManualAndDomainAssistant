# Reuse the plumbing, build the review loop

Reuse almost everything below the user interface, and build the three thin layers that make this project different. No open-source or commercial product can serve as the Downloader, the Assistant or the Reviewer, because none treats "an AI proposal, plus its evidence span from a manual, plus its confidence, plus a quality issue" as a first-class reviewable object. TermIt comes closest on document-grounded terms, and VocBench 3 closest on change-level approval, but neither has AI features or git as its source of truth ([TermIt](https://github.com/kbss-cvut/termit); [FAO AIMS on VocBench](https://www.fao.org/agrovoc/node/26)). The library layer, by contrast, is mature, permissively licensed and was actively released in 2026. **Python apps can stand on rdflib 7.6, pyoxigraph 0.5.13, pySHACL 0.40.2, LinkML 1.12.1, OAK 0.7.4 and Docling. The TypeScript Reviewer can stand on N3.js, @zazuko/env, shacl-engine, Reactodia, Cytoscape.js and React Flow. The Assistant's in-answer diagrams can come from Mermaid 12.3, fed by deterministic templates. The shared infrastructure is an Oxigraph server with named graphs, plus a ROBOT + pySHACL + pyLODE CI pipeline over git.** Under the monorepo rule "apps share data, not components", the shared layer is formats and contracts: a LinkML schema, SHACL shapes, a quality-issue vocabulary, a named-graph naming scheme and KGCL change records. Each app generates its own code from these and picks its own libraries. The commercial suites (TopBraid EDG, PoolParty 10, metaphactory 6, Semaphore 5.10) already ship LLM-assisted modeling with human review, but they are closed source, quote-priced and git-secondary. Mine them for UX patterns in a time-boxed trial; do not depend on them. The biggest risks are a single-maintainer core component (Reactodia, 39 stars), weak-copyleft licences (Reactodia LGPL-2.1, elkjs EPL-2.0) and the restrictive licence terms on several "free" tools (GraphDB 11 Free, Neo4j NVL). A two-week block of spikes will retire most of them.

This report specialises the toolchains from the earlier reports for the three-app experimental monorepo. Those reports are *Knowledge graphs for domain assistants* (the deterministic spine and the Reviewer design), *Enterprise platform domain assistants* (the harvest-propose-review toolchain and the five view templates), *Ontology change management in git* (serialization, CI stages and the tools to avoid) and *Domain assistants for emerging cross domains* (the experimentation harness). It does not re-derive their architecture. Where they named a tool, this report checks its 2026 status and either confirms it or replaces it.

## Three apps, three verdicts: reuse libraries, build the app-specific layer

The answer differs by app because each app's unique value sits at a different height in the stack. The Downloader's value is in the extraction pipeline, which libraries cover well. The Assistant's value is in retrieval routing and answer composition, where frameworks exist but the earlier evidence argues against adopting them wholesale. The Reviewer's value is a review workflow that no product models, so it is the app with the most custom code.

The Reviewer verdict is the consequential one. The earlier Reviewer design requires the review queue and its state to live in a database, evidence spans to be string-matched to the source, the agent never to commit, and approved decisions to become regression tests. None of the editors below exposes those hooks, while the component libraries let the project build them in weeks.

## No editor models "proposal plus evidence plus issue", so editors become side tools

Every editor surveyed implements one of three review semantics. The project needs all three, joined to AI proposals. **Change-level validation** is VocBench 3's model: each edit stays pending until a validator accepts it. That is the closest match to reviewing individual AI proposals, but the triple store, not git, is the source of truth ([FAO AIMS](https://www.fao.org/agrovoc/node/26)). **Concept-level status** (draft or candidate, then approved or rejected) appears in OpenMetadata, TemaTres and TermIt. OpenMetadata's version is the cleanest: with reviewers assigned, a new term starts as a draft and creates an approval task that only reviewers can close ([OpenMetadata approval docs](https://docs.open-metadata.org/v2.1.x-SNAPSHOT/how-to-guides/data-governance/glossary/approval)). **File-level PR review** is the voc4cat and SkoHub pattern: SKOS Turtle in git, CI validation, and approval as a merged pull request ([voc4cat-tool](https://github.com/nfdi4cat/voc4cat-tool); [skohub-vocabs](https://github.com/skohub-io/skohub-vocabs)). Only the third matches the project's "approvals as git PRs" rule. So the Reviewer builds the first two semantics in its own queue and uses the third as the final gate.

The OWL reasoning layer is the exception to the "actively released" pattern. The OWL API's last release is 5.5.1 from 2024, ELK 0.6.0 is from 2024, HermiT's Maven artifact dates from 2020, and Openllet's last release was 2019 ([OWL API on Maven](https://repo1.maven.org/maven2/net/sourceforge/owlapi/owlapi-distribution/maven-metadata.xml); [ELK](https://github.com/liveontologies/elk-reasoner); [Openllet](https://github.com/Galigator/openllet)). This layer is stable but rarely released, so treat it as a frozen dependency reached only through ROBOT in CI. That also matches the earlier finding that the graph or reasoner computes inferences, the LLM only explains them, and inferences should be materialised at release time rather than computed per question.

The extraction-framework landscape splits into two families. **Schema-grounded** frameworks are OntoGPT/SPIRES, LlamaIndex's `SchemaLLMPathExtractor`, neo4j-graphrag's schema pipeline and DSPy signatures over LinkML-generated Pydantic models. **Schema-light** GraphRAG engines are Microsoft GraphRAG 3.3, LightRAG 1.5.7, Cognee 1.6.8, Graphiti 0.31.2 and KGGen ([GraphRAG](https://pypi.org/project/graphrag/); [LightRAG](https://pypi.org/project/lightrag-hku/); [Cognee](https://pypi.org/project/cognee/); [Graphiti](https://pypi.org/project/graphiti-core/)). The Downloader belongs firmly in the first family, because the earlier architecture "types into" a seeded core ontology and sends new types to review. The second family produces ungoverned graphs that would bypass the Reviewer. No maintained LLM-specific glossary or term-extraction library was found, so term extraction is simplest as one more LinkML/DSPy extraction task, unioned with statistical candidates for recall.

### The triplestore is the one shared runtime service

Oxigraph is the lightest fully open choice for both the embedded and server roles. It implements the SPARQL 1.1 Protocol and Graph Store Protocol over named-graph quads under MIT/Apache-2.0, and v0.5.13 was released 2026-10-22 ([Oxigraph](https://github.com/oxigraph/oxigraph)). The Downloader can use pyoxigraph embedded for scratch work and then push run graphs over the Graph Store Protocol. The Assistant and Reviewer reach the same server over HTTP. Fuseki 6.2 is the fallback if server-side SHACL, text indexing or a mature admin UI becomes necessary ([Fuseki on Maven](https://repo1.maven.org/maven2/org/apache/jena/jena-fuseki-server/maven-metadata.xml)). QLever 0.6.0 (Apache-2.0) is the option for very large read-heavy graphs ([QLever](https://github.com/ad-freiburg/qlever/releases)). Staying on standard SPARQL 1.1 plus the Graph Store Protocol keeps the store swappable. That matters, because SPARQL 1.2 is still a Working Draft dated 12 November 2026, so triple terms should not be load-bearing yet ([SPARQL 1.2](https://www.w3.org/TR/sparql12-query/)). The first report's sketch of a Neo4j property graph as the operational KG is superseded here, as the later reports already did. The project now holds harvested data in a triplestore with named graphs. Neo4j plus neosemantics stays a fallback only if the project later adopts property-graph tooling ([neosemantics](https://github.com/neo4j-labs/neosemantics)).

For the Assistant, the earlier enterprise report already specified the pipeline: SPARQL CONSTRUCT, a serializer to Mermaid or DOT, and a parser check before sending, all capped at about 15–30 nodes. The libraries confirm that this works with standard parts. Mermaid's strict security level HTML-encodes labels and disables clicks, which neutralises cross-site scripting from LLM-paraphrased labels. Answer-sized diagrams stay far below its 500-edge default ([Mermaid config](https://mermaid.js.org/config/schema-docs/config.html)). LinkML's `gen-erdiagram` adds deterministic schema snippets for free ([LinkML generators](https://linkml.io/linkml/generators/index.html)). Where an answer needs "click to expand", the same JSON graph renders in Cytoscape.js with a dagre layout.

The Reviewer needs three kinds of view, and no single library covers them all. **Reactodia is the only maintained, open, RDF-native, React-embeddable graph workspace.** Its changelog shows the primitives a review tool needs: authoring of entities and relations with `applyAuthoringChanges()` (0.31), validation results with severity levels and related-property IRIs that re-validate on undo/redo (0.33), and diagram-only annotations ([CHANGELOG](https://github.com/reactodia/reactodia-workspace/blob/master/CHANGELOG.md)). Whether it can display an externally computed SHACL report is inferred from the changelog, not demonstrated, which makes it the first spike. **Cytoscape.js** carries the issue triage and diff views: selectors such as `.shacl-violation`, `.duplicate-candidate` and `.added`/`.removed` cover overlays without custom rendering, and compound nodes model merge-candidate clusters. **React Flow** suits the card-style decision surface. No library ships a graph diff view, and no off-the-shelf visual OWL/SKOS diff exists. The diff is custom work: compute the triple delta (the CI already produces `robot diff`), then render a union graph with status classes. The SHACL-violation workbench should re-implement SHACLens's coordinated views (class tree with violation counts, filterable table, node-link drill-down, LLM explanation). SHACLens is a 2026 research workflow with no reusable package or clear source licence ([SHACLens paper](https://www.frontiersin.org/journals/bioinformatics/articles/10.3389/fbinf.2026.1756507/full)).

## Shared contracts, not shared code: the recommended stack

The monorepo rule removes the usual temptation to build a shared "ontology SDK". What the three apps must agree on is data at rest and on the wire. Under Specification-Driven Development, each contract below is a spec artifact in its own right that the app specs reference. Each app generates or hand-writes its own bindings. A Python package imported by two apps, or an npm component used by both the Assistant and the Reviewer, would break the rule. A LinkML schema from which each app generates its own Pydantic or TypeScript types does not.

| Shared contract or service | Format / tool | Owner and consumers |
|---|---|---|
| Domain and extraction schema | LinkML YAML (Term, Concept, Definition, Relation, Evidence span, Proposal, QualityIssue); generated OWL, SHACL and JSON-LD context built in CI | Curated in git; Downloader generates Pydantic; Reviewer generates TS types; Assistant generates Pydantic or uses SPARQL directly |
| Curated knowledge | Canonical Turtle (OWL, SKOS, SHACL), one file per module, serialized by a pinned Cool RDF or rdf-toolkit (per the change-management report) | Git; read by all apps from released bundles loaded into the store |
| Quality rules | SHACL shapes in `shapes/`; pySHACL is the validator of record | Downloader runs them on candidates; CI on curated data; Reviewer previews with shacl-engine |
| Quality-issue vocabulary | Small OWL/SKOS vocabulary extending `sh:ValidationResult` with issue type (gap, contradiction, drift, undefined term), severity, evidence spans and affected IRIs | Written by the Downloader, shown by the Assistant, triaged by the Reviewer |
| Named-graph scheme | IRIs per extraction run (candidates + PROV-O), per review state, per curated release, per quality-issue run | Oxigraph server; every app reads and writes by convention |
| Change records | KGCL YAML per PR, applied with OAK (per the change-management report) | Reviewer writes; CI builds the changelog |
| Answer stamp | Release version + git commit + data snapshot IRI per answer | Assistant writes; Reviewer and evaluation read |
| Infrastructure | Oxigraph server in Docker Compose; CI on GitHub Actions; Skosmos or SkoHub for publishing; OLS4 MCP (hosted) | Shared services, not shared code |

**Downloader (Python).** Docling → deterministic structure extractor → LinkML-generated Pydantic targets driven through DSPy (or OntoGPT/SPIRES, decided by a spike) → rdflib serialization into a per-run named graph with PROV-O → pySHACL rules plus rule-blocked contradiction candidates written as quality issues → OAK or OntoAligner mapping suggestions. pyoxigraph serves as the local working store.

**Assistant (Python backend, thin web frontend).** A hybrid retriever (dense + BM25 + reranker) over chunks with heading-path prefixes. Glossary normalisation via SPARQL over the released SKOS graph. A question router that adds templated SPARQL for relational, comparison and version questions. Mermaid rendering in strict mode from deterministic templates. OLS4 MCP for external grounding, and a thin custom MCP server over Oxigraph built with the official SDK if the agent needs tools ([OLS4](https://github.com/EBISPOT/ols4); [MCP SDK](https://www.npmjs.com/package/@modelcontextprotocol/sdk)). sib-swiss/sparql-llm (MIT) is the most credible maintained component for improving LLM-generated SPARQL if free-form querying is ever tested ([sparql-llm](https://github.com/sib-swiss/sparql-llm)). LightRAG, GraphRAG and LlamaIndex graph indexes enter only as factor-screening arms in the evaluation harness.

**Reviewer (TypeScript/React frontend, backend of its own choosing).** Reactodia workspace behind an adapter. Cytoscape.js triage and diff views. React Flow decision cards. shacl-form for edit dialogs. A d3-hierarchy tree for SKOS. N3.js, @zazuko/env, jsonld.js and shacl-engine for client-side RDF. The backend holds the review queue (state in a database, not in the LLM context), applies decisions as KGCL with OAK or as SPARQL Update, runs the pinned serializer, and opens PRs through the git host's API. If that backend is Python, it reuses the Downloader's *choice* of rdflib and OAK, not its code.

**CI (shared infrastructure).** The ten-stage pipeline from the change-management report stands unchanged: canonical-serialization check, LinkML lint and generation, `robot reason` with ELK, `robot report`, pySHACL, deprecation lint, competency-question regression, breaking-change floor, overlap check and `robot diff` as a PR comment. Releases add pyLODE or Widoco documentation, SHACL Play shape docs and a Skosmos/SkoHub rebuild. ODK is optional; its OBO conventions add friction for a generic SKOS/OWL project, which remains unevaluated.

One trade-off needs an explicit owner. Running pySHACL in the Downloader and CI and shacl-engine in the Reviewer means two SHACL engines interpret the same shapes, and they can disagree on edge cases. The contract should state that pySHACL is authoritative and that Reviewer results are previews. A conformance test that runs the shapes through both engines on shared fixtures catches drift.

The weak-copyleft dependencies need a decision, not avoidance. Reactodia (LGPL-2.1) is acceptable as an unmodified, dynamically bundled npm dependency, provided users can replace the library. elkjs (EPL-2.0) is file-level copyleft and normally fine unmodified. owlready2 and py-horned-owl are LGPL-3.0. TermIt (GPL-3.0) matters only if it is embedded or modified. An internal experiment carries little exposure, but if the project could ever be distributed, a one-time legal read now is cheaper than a rewrite later. Keep Reactodia unmodified and behind an adapter in any case. That handles both the licence question and the bus-factor risk of a 39-star project.

## Commercial suites buy breadth the experiment does not need yet

Buying a suite would trade the project's three distinguishing properties for features it can defer. PoolParty, EDG, metaphactory and Semaphore cover AI-assisted proposals, review workflows and diagrams out of the box, and their 2026 releases are converging on exactly the Reviewer concept. All of them are quote-priced with no public list prices. They keep their own store or "asset collections" as the primary record, with git integration secondary or unverified. They cannot be embedded as modules of a single-repo monorepo. And their AI features are vendor-claimed with no independent evaluation. Stardog's own documentation admits its Voicebox output "may contain hallucinations" despite "hallucination-free" marketing ([Atlan, a competitor](https://atlan.com/know/ai-agent/knowledge-graph/what-is-stardog/)). The commercial graph-visualisation SDKs (yFiles for HTML, Ogma, KeyLines/ReGraph) are also quote-only. yWorks is moving new purchases to term licences, at least for yFiles.NET ([yFiles.NET SLA](https://www.yworks.com/products/yfiles-net/sla)).

The case for buying would strengthen under three conditions: the experiment graduates to an enterprise rollout with dozens of curators, the organisation already licenses one of these suites, or open-source layout and diff quality proves insufficient for governance views at scale. Even then, the project's contracts would survive the switch, because every suite imports SKOS, OWL and SHACL. That is the practical payoff of standard formats in git. The cost-effective use of vendors now is a **time-boxed UX benchmark**: one or two vendor demos or trials (PoolParty 10.1's Taxonomy Builder and metaphactory 6.0's modeling agent are the most relevant) to capture interaction patterns for proposal review, then close the trial.

Several questions remain open after the notes. Is the Skosmos licence really MIT, given GitHub reports NOASSERTION? Does WebProtégé's new microservice stack expose a stable API? ## Conclusion

The ecosystem has moved since the semantic-web tooling era: the library layer is no longer the bottleneck, and the editors are no longer the product. Python and TypeScript RDF stacks, SHACL engines, LinkML generators and ROBOT all shipped in the months before this check, under licences that pose no problem. Meanwhile every commercial suite is racing to add the "LLM proposes, human approves" loop. The project's leverage is therefore not in choosing a platform but in the contracts. A LinkML schema, SHACL shapes, a quality-issue vocabulary, a named-graph convention and KGCL change records are what let three independently built apps cooperate without sharing code. They also keep a later switch to a commercial suite cheap.

One implication runs against intuition. The most reused component in the Reviewer, Reactodia, is also the most fragile: it carries a single-maintainer bus factor, pre-1.0 APIs and an LGPL licence. Meanwhile the most custom code (the queue, the evidence model, the diff) sits on the least risky foundations. Isolating Reactodia behind an adapter, and making spike 1 the first task, turns the project's largest dependency risk into a two-day experiment.
